## 1. Verified Compilers to Arithmetic / Boolean Circuits

### CircGen / Almeida et al. (CCS 2017)
**"A Fast and Verified Software Stack for Secure Function Evaluation"**
Almeida, Barbosa, Barthe, Dupressoir, Grégoire, Laporte, Pereira
*ACM CCS 2017*
https://eprint.iacr.org/2017/821

Verified C → Boolean circuit compiler (CircGen, built on CompCert) plus verified Yao garbled circuit protocol. EasyCrypt + Coq proofs. Target is MPC/garbled circuits, not ZK arithmetic circuits. Closest historical predecessor: first machine-checked compiler-to-cryptographic-constraint result.

**Relation to Heyting**: same verified-compiler tradition; different target (Boolean/MPC vs arithmetic/ZK) and different proof methodology (EasyCrypt vs Lean 4 dependent types).

---

### CirC (IEEE S&P 2022)
**"CirC: Compiler infrastructure for proof systems, software verification, and more"**
Ozdemir, Brown, Wahby
*IEEE S&P 2022*
https://eprint.iacr.org/2020/1586

Shared compiler IR (existentially quantified circuits, EQC) targeting R1CS, SMT, and ILP. Feature-complete Circom compiler in ~900 LOC vs reference compiler's ~24 000 LOC. No machine-checked correctness proofs; correctness argument is informal. Focus: compiler engineering and extensibility, not formal guarantees.

**Relation to Heyting**: same pipeline goal (high-level → R1CS); orthogonal methodology. CirC provides infrastructure, Heyting provides verified guarantees. A natural future combination.

## 2. Formal Verification of ZK Circuits / R1CS Gadgets

### QED² (PLDI 2023)
**"Automated Detection of Under-Constrained Circuits in Zero-Knowledge Proofs"**
Pailoor, Chen, Wang, Rodríguez, Van Geffen, Morton, Chu, Gu, Feng, Dillig
*PACMPL (PLDI) 2023*
https://doi.org/10.1145/3591282

SMT-based tool for finding under-constrained Circom circuits. Verifies *output* circuits for uniqueness (no two distinct witnesses for same input), not compiler correctness. Found 8 previously unknown vulnerabilities in widely-used Circom circuits. Directly motivates the need for compiler-level guarantees.

**Relation to Heyting**: complementary. QED² checks output circuit properties; Heyting proves the compiler preserves and reflects satisfiability end-to-end. Both are necessary: Heyting does not guarantee the source circuit is bug-free, only that compilation adds/removes no constraints.

---

### Coglio et al. (ePrint 2023/1278)
**"Compositional Formal Verification of Zero-Knowledge Circuits"**
Coglio, McCarthy, Smith, Chin, Gaddamadugu, Dellepere (Aleo / Kestrel Institute)
*ePrint preprint, 2023 — check for published venue*
https://eprint.iacr.org/2023/1278

ACL2-based formal specification and verification of R1CS gadgets generated by Aleo's snarkVM. Compositional: gadgets are verified independently and composed. Verifies *individual gadgets*, not the full compiler pipeline or end-to-end preservation. Labeled "preliminary report" — check if full version appeared.

**Relation to Heyting**: gadget-level vs pipeline-level verification. ACL2 vs Lean 4. Coglio et al. verify the target artefacts; Heyting verifies the compiler transformation.

## 3. Closely Related: Verified ZKP Compilers in Lean 4

### Clap-lean (ongoing, 2024–)
**"Clap: a Semantic-Preserving Optimizing eDSL for Plonkish Proof Systems"** (arXiv 2024)
Stronati, Firsov, Locascio, Livshits
arXiv:2405.12115
https://arxiv.org/abs/2405.12115
Lean 4 implementation: https://github.com/Clap-lang/clap-lean

**This is the closest related work. Read carefully.**

The arXiv paper describes a Rust eDSL targeting Plonkish circuits with informal soundness/completeness claims. The Lean 4 repository is a complete redesign: a Lean 4 eDSL with machine-checked proofs.

**What the Lean 4 repo actually proves** (verified by reading source):
- `soundness`: Circuit → Cs (constraint system) compilation is sound via `wrBisim` (right-weak bisimulation). If the Cs accepts, the original Circuit accepts.
- `completeness`: `wrap toWg toCs` is equivalent to the original Circuit evaluation. Witness generator + constraint system are jointly complete.
- Both proofs are structural induction over the Circuit IR, covering all constructors: `nil`, `lam`, `eq0`, `share`, `isZero`, `num2bits`.
- Circuit operations: `isZero`, `num2bits`, `share` (more than Heyting currently covers in LLZK).
- Executable: snarkjs integration (`runSnarkjs.sh`), R1CS serialization (`R1Serialize/`).
- README: *"Future work aims to prove functional correctness of the source circuits."*

**Sorry status**: unknown — needs `grep -r "sorry" Clap/` on the repo before claiming superiority.
**Axiom footprint**: unknown — needs `#check_axioms` audit.
**Correctness notion**: `wrBisim` (right-weak bisimulation) — the Cs may take more inputs than the Circuit; the Circuit "waits" while the Cs receives extra witness values. This asymmetry is intentional and correct for the compilation scheme.

**Key differences from Heyting**:

| Dimension | Clap-lean | Heyting |
|---|---|---|
| Source language | Clap's own Circuit eDSL | LLZK IR (Veridise/Boa upstream) |
| Target | `Cs` + `Wg` (own format) | FlatIR → R1CS (Circom-compatible binary) |
| Correctness notion | `wrBisim` (asymmetric) | `PresReflPass` (symmetric preservation + reflection) |
| Pipeline depth | 1 pass (Circuit → Cs) | 3 passes (StructIR → FlatIR → R1CS), composed |
| Field-generic | yes (`ZMod p`) | yes (`F : Type [Field F]`) |
| Circuit operations | `isZero`, `num2bits`, `share` | felt ops, struct calls, readMember |
| Proof assistant | Lean 4 + Mathlib | Lean 4 + Mathlib |
| Sorry status | unknown | 0 (audited) |
| Axiom footprint | unknown | `propext`, `Classical.choice`, `Quot.sound` |
| Source: real upstream IR | no | yes (LLZK from independent team) |

**Differentiator narrative for the paper**: Clap-lean is concurrent work in the same Lean 4 space proving similar properties. Heyting differs in (1) compiling a real upstream IR designed by an independent team, not a co-designed eDSL; (2) proving a symmetric preservation+reflection equivalence rather than an asymmetric bisimulation; (3) a three-pass composed pipeline whose correctness is itself composed; (4) explicitly audited zero-sorry, standard-axioms-only guarantees.

## 4. ZKP DSLs and Compilers (Unverified)

### Circom
Bellés-Muñoz, Baylina et al. De facto standard DSL for R1CS circuits. No compiler correctness proof. Source of most known ZKP bugs cited in the vulnerability literature. Heyting's LLZK IR is designed to be a target for Circom-like frontends.

### ZoKrates (iThings 2018)
"ZoKrates — Scalable Privacy-Preserving Off-Chain Computations"
Eberhardt, Tai
https://doi.org/10.1109/Cybermatics_2018.2018.00199
High-level language → R1CS. No mechanized correctness.

### Leo / Aleo
"LEO: A Programming Language for Formally Verified, Zero-Knowledge Applications" (Chin, 2021)
https://docs.zkproof.org/pages/standards/accepted-workshop4/proposal-leo.pdf
Despite "formally verified" in the title, verification is aspirational at the language level; Coglio et al. (2023) is the actual ongoing verification effort for Aleo's backend.

### Snarky (o1 Labs)
OCaml eDSL for SNARK circuits in the Mina protocol. Unverified compiler.

### Noir (Aztec)
Rust-based ZKP DSL. No formal compiler verification. Compiler bug disclosures in 2022.

### Tabby (OOPSLA 2025)
"Tabby: A Synthesis-Aided Compiler for High-Performance Zero-Knowledge Proof Circuits"
Junrui Liu, Jiaxin Song, Yanning Chen, Hanzhi Liu, Hongbo Wen, Luke Pearson, Yanju Chen, Yu Feng
*PACMPL (OOPSLA) 2025*
https://dl.acm.org/doi/10.1145/3763110
PDF: https://chyanju.github.io/publications/oopsla25-tabby.pdf

Synthesis-aided compiler: domain-specific IR + sketch-based program synthesis + SMT-based equivalence checking → optimized low-level circuits. Correctness argument is SMT-checked semantic equivalence, not machine-checked proof. Focus: performance (circuit size, proof generation time).

**Relation to Heyting**: same pipeline ambition; orthogonal methodology. Tabby optimizes; Heyting proves. Tabby's SMT equivalence checking is not kernel-verified — if the SMT solver has unsound theories or times out, the guarantee fails. Heyting's preservation+reflection proofs are verified by the Lean kernel unconditionally.

## Related Work

**Verified compilers for cryptographic constraint systems.**
The closest prior work is Clap-lean [CITE], a concurrent Lean 4 formalization of a ZKP circuit compiler. Clap-lean proves soundness via a right-weak bisimulation (`wrBisim`) and completeness via a wrap-based equivalence for a co-designed circuit eDSL. Our work differs in three ways. First, we compile LLZK, an IR designed independently by the Veridise/Boa team; Clap-lean compiles its own eDSL, making our correctness claim extrinsic to the compiler's design. Second, our correctness notion is symmetric: `PresReflPass` requires both preservation (source sat → target sat) and reflection (target sat → source sat) with explicit witness relations, whereas `wrBisim` is asymmetric by design. Third, our pipeline composes three passes (StructIR → FlatIR → R1CS) using `PresReflPass.compose`, proving end-to-end correctness structurally.

An earlier verified compiler for cryptographic circuits is CircGen [CITE], which targets Boolean circuits for Yao's garbled-circuit protocol and is verified using EasyCrypt and CompCert. CircGen targets MPC, not ZK proof systems, and the target is Boolean rather than arithmetic. CirC [CITE] provides compiler infrastructure for proof systems (R1CS, SMT, ILP) and achieves good performance, but carries no machine-checked correctness proofs.

**Formal verification of ZK circuit artefacts.**
QED² [CITE] detects under-constrained Circom circuits via SMT-based uniqueness analysis. It verifies properties of *output* circuits, not the compiler transformation. Our work is complementary: Heyting guarantees compilation adds and removes no constraints, but does not verify that source circuits correctly encode the intended computation. Coglio et al. [CITE] verify R1CS gadgets generated by Aleo's snarkVM compositionally in ACL2, checking individual gadgets rather than the full compilation pipeline. Circomspect [CITE] performs static under-constraint analysis on Circom source. AC4 [CITE] provides algebraic constraint checking.

**Synthesis-aided and optimizing ZKP compilers.**
Tabby [CITE] uses sketch-based program synthesis and SMT-based equivalence checking to derive optimized ZK circuits from high-level code. Its correctness argument relies on the SMT solver; ours relies on the Lean kernel. Clap (Rust) [CITE] frames compilation as a semantic-preserving problem and claims informal soundness and completeness for Plonkish systems; the Lean 4 redesign (Clap-lean) mechanizes these claims as described above.

**ZKP domain-specific languages.**
Circom [CITE], ZoKrates [CITE], Noir, Snarky, and Leo are widely-used ZKP DSLs that compile to arithmetic circuits without machine-checked compiler correctness. The vulnerability disclosures motivating this line of work include under-constrained circuits in Tornado Cash (2019), Zcash (2019), Aztec (2022), and Noir (2022) [CITE QED²].

**Compiler correctness frameworks.**
Our `PresReflPass` is inspired by Abate et al.'s [CITE] trinitary compiler correctness framework (TPσ ↔ CC~ ↔ TPτ), instantiated in `Heyting/Core/TrinitaryCC.lean`. The verified-compiler tradition traces to CompCert [CITE], though our setting (field arithmetic, dependent-type intrinsic well-formedness) requires new proof techniques.
